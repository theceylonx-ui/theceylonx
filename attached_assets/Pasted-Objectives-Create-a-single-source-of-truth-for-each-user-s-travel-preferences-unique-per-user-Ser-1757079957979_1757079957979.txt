Objectives
Create a single source of truth for each user’s travel preferences (unique per user).
Server-side strict validation + canonicalization (no dupes, no unknown values).
Frontend Profile → Preferences tab that displays, edits, and saves reliably.
On save, trigger recompute/invalidate for personalized recommendations and refresh UI.
Backfill/cleanup legacy data; fix previous “not updating” bug.
Full test coverage: unit, API, and E2E. Clear logs for diagnostics.
Data Model (Drizzle / Postgres)
Enums / Taxonomy
Create a small taxonomy module on the server so values are controlled (no free-text in DB).
vibe: e.g., relaxed, adventure, culture, beach, nature, nightlife, wellness
companions: solo, couple, friends, family, senior_friendly
interests: hiking, wildlife, history, photography, food, diving, surfing, temples, festivals, wellness, ayurveda, train_journeys
when: store months or seasons. Use months for precision: jan…dec (lowercase slugs).
Keep taxonomy in code: /server/config/preferences_taxonomy.ts. Server rejects unknowns.
Table: user_preferences
user_id UUID PRIMARY KEY (exactly one row per user)
vibe text[] (deduped, sorted)
companions text[] (deduped, sorted)
interests text[] (deduped, sorted)
months text[] (subset of ['jan'..'dec'], deduped, sorted)
regions text[] (optional; if used → controlled list: north, east, south, west, hill_country, cultural_triangle, colombo)
budget_min int NULL
budget_max int NULL
version int DEFAULT 1 (for optimistic concurrency)
updated_at timestamptz DEFAULT now()
Indexes
PK (user_id)
GIN indexes on arrays if needed for analytics: (vibe), (interests)
Constraint
CHECK (budget_min IS NULL OR budget_max IS NULL OR budget_min <= budget_max)
Table: preference_events (audit & ML signal)
id pk
user_id
event enum: created | updated | reset
diff JSONB (old→new)
created_at timestamptz DEFAULT now()

Server (Express + TS)
Validation & Canonicalization
Create /server/modules/preferences/schema.ts with Zod:
Accept arrays; lowercase + slugify inputs; deduplicate; sort canonically.
Reject any value not in taxonomy; return 422 with details.
// Pseudo: canonicalizeArray(input, allowedSet) => sorted unique array of allowed values
Auth & Ownership
All GET/PUT routes require Clerk auth.
Write requires email verified (server-side check using Clerk SDK).
Only the owner (req.auth.userId) can read/write their preferences unless role=admin.
Routes
GET /api/users/me/preferences
If no row → return { empty: true, defaults: { … } } (client can display placeholders).
PUT /api/users/me/preferences
Body: validated payload; server canonicalizes.
Optimistic concurrency: accept optional If-Match: <version> header. If provided and mismatches current version → 409 Conflict with { expectedVersion, actualVersion }.
Upsert pattern: if row exists → update + version = version + 1.
Write preference_events with diff (old vs new).
Trigger ML refresh (see below).
Respond with the canonical saved object + new version.
POST /api/users/me/preferences/reset (optional)
Clear to defaults; write event; trigger ML refresh.
ML Refresh (critical)
Add a small service /server/services/recs.ts:
recs.invalidateUser(userId) → clear any cache keys (e.g., redis.del("recs:"+userId)).
recs.enqueueRecompute(userId) → push a job to your existing ML queue (BullMQ/Worker). If no queue, call the ML service endpoint POST /ml/recomputeUser with { userId } (idempotent).
In PUT/reset, call:
await recs.invalidateUser(userId)
await recs.enqueueRecompute(userId)
Return immediately to UI; don’t block on full recompute. UI can refetch recs (see Frontend).
